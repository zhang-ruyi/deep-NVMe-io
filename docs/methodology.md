# Methodology

## 1. Layers

```
fio -> VFS/ext4 -> block layer bio -> block request -> nvme driver -> SQ/CQ -> PCIe -> NVMe device
```

The scripts capture three software-visible boundaries:

| Layer | Trace / probe | What it shows |
|---|---|---|
| bio | `block:block_bio_queue` | bio size, sector, rwbs, submitting comm |
| request | `block:block_rq_issue` | after merge/split; bytes, sector, rwbs |
| NVMe I/O command | `nvme:nvme_setup_cmd` | qid, cmdid, nsid, opcode, slba, len (NLB) |
| NVMe completion | `nvme:nvme_complete_rq` | qid, cmdid, result, retries, status |
| full 64B SQE | kprobe `nvme_queue_rqs` / `nvme_queue_rq` | PRP1/PRP2, NLB, CID, control |
| batch / submit | kprobe `nvme_queue_rqs`, `nvme_submit_cmds.part.0` | requests per batch and submit calls |
| admin | qid 0 in `nvme_setup_cmd` / `nvme_complete_rq` | Identify, Get Log Page, Get Features, ... |

`qid=0` is the admin queue. `qid>=1` are I/O queues.

## 2. SQE layout used by the decoder

In the 64-byte NVMe read/write command:

| Offset | Field |
|---:|---|
| 0 | opcode (`0x01` write, `0x02` read, `0x00` flush) |
| 1 | flags |
| 2..3 | command ID |
| 4..7 | NSID |
| 8..15 | cdw2/cdw3 |
| 16..23 | metadata |
| 24..31 | PRP1 |
| 32..39 | PRP2 |
| 40..47 | SLBA |
| 48..49 | NLB (zero-based) |
| 50..51 | control |
| 52..55 | DSMGMT |
| 56..59 | reftag |
| 60..63 | LBAT/LBATM |

Data bytes = `(NLB + 1) * 512`. PRP1/PRP2 are DMA addresses. With an active IOMMU they are IOVAs, not physical addresses.

## 3. Reconciliation rules

Do not compare fio IO count directly with NVMe command count. Use:

```
bio count -> block_rq_issue count -> nvme_setup_cmd count (qid >= 1)
```

- `block_rq_issue` is already after merge/split.
- One request normally becomes one NVMe I/O command.
- If the driver/block layer splits a request, NVMe commands > block requests.
- If bios merged before issue, bio count > block request count.
- Sum `bytes` across requests and compare with `(NLB+1)*512` across NVMe commands.
- For a 1:1 check, `block sector + partition_start_sector == nvme slba`.
- Filter `qid=0` out of data statistics and report admin separately.
- Flush has no data: block rwbs contains `F`, NVMe opcode `0x00`, NLB field is not a data length.
- Discard/TRIM maps to DSM or Write Zeroes; it is not a data read/write.

## 4. Current observations

### 4.1 block request and NVMe command are 1:1

In all 24 phases of the matrix, fio data commands have:

```
block_rq_issue count == nvme_setup_cmd(qid>=1, write/read) count
```

with the same per-command size. No merging was observed under `scheduler=none`, `direct=1`, `iodepth=8`.

### 4.2 512B write is not fio 1:1

For a 16 MiB 512B write:

- fio reports 32,768 IOs;
- block layer and NVMe layer each see 36,864 commands:
  - 32,768 × 512B (NLB=0);
  - 4,096 × 3,584B (NLB=6) starting at sector 1 of every 4 KiB block.

The 3,584B writes overlap sectors 1..7 of each 4 KiB block. They are submitted from the fio task and are visible at both block and NVMe layers. Therefore:

- `block_rq_issue == nvme_setup_cmd` still holds;
- `fio IO != block/NVMe` for this row;
- DMA bytes become 30.0 MiB for a 16.0 MiB fio workload (`dma_amp=1.875`).

This is most likely ext4/iomap handling of sub-4KiB direct writes. Confirm with another filesystem (XFS) or a raw namespace before generalizing. 512B read is clean 1:1.

### 4.3 256KiB and above are split

- `max_sectors_kb=128`, `max_hw_sectors_kb=128`, `max_segments=33`.
- 256KiB: 2 × 128KiB requests/commands per fio IO.
- 512KiB: 4 × 128KiB.
- 1MiB: 8 × 128KiB.
- NVMe MDTS=6 (256KiB) but the block queue limit is stricter, so no 256KiB NVMe data command is generated by fio here.

### 4.4 Submission batching

`nvme_queue_rqs` is used, but under this workload almost all batches contain one request:

- 131,586 queue_rqs calls, 135,682 commands;
- batch length 1: 127,490; length 2: 4,096; length >2: 0;
- 131,586 `nvme_submit_cmds.part.0` calls;
- 1.031 commands per submit/doorbell group.

All 4,096 length-2 batches come from the 512B write anomaly: one 3,584B extra write is batched with one 512B write.

### 4.5 Admin

Admin commands are on qid 0 and do not come from block bios:

| command | data bytes | status |
|---|---:|---|
| `nvme_admin_identify` (CNS=1) | 4096 | 0x0 |
| `nvme_admin_get_log_page` | 512 | 0x0 |
| `nvme_admin_get_features` | 0 | 0x0 |

The block layer shows them as `block_rq_issue: 0,0 N <bytes>`, but there is no `block_bio_queue`. During the fio matrix, qid 0 count was 0.

## 5. DMA and PRP

- 512B..4KiB: PRP1 only, one page.
- 8KiB: PRP1 + PRP2 (second page).
- 16KiB+: PRP1 + PRP2 pointing to a PRP list:
  - 16KiB: 4 pages, list of 3 entries;
  - 32KiB: 8 pages, list of 7;
  - 64KiB: 16 pages, list of 15;
  - 128KiB: 32 pages, list of 31.
- 256KiB/512KiB/1MiB fio IOs become multiple 128KiB NVMe commands; each has a 31-entry PRP list.

For a write command the device reads host memory; for a read command the device writes host memory. SQ fetch, CQE write and MSI-X are also PCIe memory transactions. The doorbell is an MMIO write.

TLP headers, tags, split/merge, MPS segmentation, ACK/NAK and exact DMA order are not visible to the OS.

## 6. Chart interpretation

- `io_layers_by_bs.svg`: log-scale counts at fio/block/NVMe boundaries. The 512B row is the only place where fio differs from the other two.
- `nvme_per_fio.svg`: commands per fio IO. 1.00 means a clean 1:1; 2/4/8 means block-layer splitting.
- `dma_amp.svg`: NVMe DMA bytes divided by fio bytes. Only 512B write exceeds 1.0 in this dataset.
- `nlb_prp.svg`: NLB, bytes per command, pages and PRP mode.
- `batch_doorbell.svg`: queue_rqs batch length distribution and submit-call ratio.
- `throughput_by_bs.svg`: 16MiB micro-run bandwidth; indicative only.
